## Overview
Priority P3 · Status Pending · Effort 1.5d if it survives.
A tiny "PVU CHE Quick-Calcs" gadget: two calculators only (DIPPR property lookup + NPSHa), pure HTML/JS running natively on a SharePoint page with no server, no fetch, no storage. It is strictly conditional: the HTML-pages lane must be GA in the tenant, a local golden-value battery (Python oracle vs JS) must be green, perf on school hardware must be acceptable, and the owner must still want it after seeing Lane A — all three or the gadget dies and this phase records the kill decision.

## Requirements
Functional:
- Two calculators: DIPPR correlation evaluation (selected common compounds with committed coefficients) and NPSHa (psig/psia handled explicitly, +14.696 psia conversion).
- Equation display via pre-rendered KaTeX-to-HTML generated by a LOCAL build step (repo devDependency `katex`), inlined into the page — no client math library fetch, no handcalcs 3-stage chain.
- Per-session state named in acceptance: in-memory module variables only, cleared on reload; NO localStorage, NO sessionStorage, NO fetch, NO cookies.
- Golden-value battery: committed input grid (psig and psia cases mandatory) evaluated by BOTH the Python oracle (importing `services/perry-engine` calculation functions) and the JS port; tolerance rel 1e-6; runs as a LOCAL script.
- School-hardware load test: local Playwright with CPU throttling.
- Programmatic upload path verified (engine, APP-ONLY) BEFORE any lifecycle promises.
- Total artifact ≤ 10MB.
Non-functional: if the kill gate fails any leg, the deliverable becomes a decision note, not a gadget.

## Architecture
```
LOCAL build:  gadget/src/{dippr.js,npsha.js} + templates
               └─ node build.mjs (katex render) → gadget/dist/index.html (single file, inlined)
LOCAL battery: gadget/oracle/golden_battery.py
               └─ imports services/perry-engine core fns → expected.json
               └─ runs node gadget/src/cli-selftest.js → compares → exit 0/1
Tenant:        engine publishes single HTML page (pages lane rehearsal) → rendered by MS HTML sandbox
```

### Task 8.2 — Calculators + build pipeline
**Goal:** A single-file HTML gadget with the two calculators and pre-rendered math.
**Target files and symbols:** `gadget/src/dippr.js`, `gadget/src/npsha.js`, `gadget/build.mjs`, output `gadget/dist/index.html`.
**Steps:**
1. Port the two calculations to plain JS, transcribing formulas and constants from the Python sources (`services/perry-engine` thermo/hydraulics modules — locate exact functions via `grep -rn "def dippr\|def npsha\|npsh" services/perry-engine/` `[VERIFY-AT-EXECUTION: exact symbol names]`).
2. Author the UI (Vietnamese labels; two tabs; inputs with unit selectors; results + rendered equations + a "đổi đơn vị" hint).
3. `build.mjs`: import `katex` from repo `node_modules`, render each equation template to HTML at build time, inline everything into one file.
4. Static budget check: `du -sh gadget/dist/index.html` ≤ 10MB (expect < 300KB).
**Success criteria:** Opening `gadget/dist/index.html` from `file://` computes both calculators correctly by inspection.
**Verify:** `node gadget/build.mjs && du -k gadget/dist/index.html` → exit 0 and prints a number < 10240.

### Task 8.3 — Golden-value battery (LOCAL, mandatory psig/psia)
**Goal:** Machine proof the JS matches the Python engine on the committed grid.
**Target files and symbols:** `gadget/oracle/golden_battery.py`, `gadget/oracle/input_grid.json`, `gadget/src/cli-selftest.js`.
**Steps:**
1. Author the grid: ≥ 20 cases per calculator, including at least 5 psig-input and 5 psia-input NPSHa cases and boundary values (0 psig, vacuum, boiling).
2. Oracle: `sys.path.insert(0, 'services/perry-engine')`, import the core functions, evaluate the grid, write `expected.json`.
3. Driver runs `node gadget/src/cli-selftest.js` (which evaluates the same grid in JS and compares within tolerance), reports per-case pass/fail, exits non-zero on any failure.
4. Grep audit: `grep -nE "fetch\(|localStorage|sessionStorage|document.cookie" gadget/dist/index.html` → no hits (lane rules).
**Success criteria:** Battery all green in one run; audit clean.
**Verify:** `python3 gadget/oracle/golden_battery.py` → exit 0 and final line contains `ALL GREEN`; the grep prints nothing.

### Task 8.4 — School-hardware load test
**Goal:** Interaction latency acceptable on throttled low-end hardware.
**Target files and symbols:** `tests/e2e/gadget-perf.spec.ts` (new; Playwright `cpuThrottling: 4` context), served from `gadget/dist/`.
**Steps:**
1. Write the spec: serve `gadget/dist/` via a static server in the test, measure keystroke→result for both calculators over 5 iterations.
2. Assert p95 < 1500 ms under 4x CPU throttle.
3. `npx playwright test tests/e2e/gadget-perf.spec.ts`.
**Success criteria:** Spec green.
**Verify:** that command → exit 0.

## Risk Assessment
- MS sandbox may disallow something the build assumed (e.g. inline script nonce): discovered only at Task 8.5 — which is exactly why the upload path is proven before lifecycle promises; likelihood medium, caught before any student exposure.
- JS/Python numeric drift on tricky unit edges: battery exists to catch it; mandatory psig/psia cases target the known historical bug class (+14.696).
- Effort creep into "just one more calculator": law — two calculators only; declines recorded, not argued.
- Copyright: equations and facts are not copyrightable, and the gadget contains no corpus text or crops; coefficients transcribed are data (fine); no Perry page images.

## Security Considerations
- No network, no storage, no credentials in the gadget — the lane's constraints are the security model.
- No gateway/API access from the gadget (it cannot reach the copilot or corpus by construction).
- Uploads through the engine with APP-ONLY credentials only.
